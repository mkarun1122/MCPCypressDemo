# Cypress MCP Demo Architecture

## Purpose

This file explains the architecture and intent of the key folders in the project, especially the `mcp-server`, `prompts`, `manual-testing`, and `results` areas. It is designed to help new contributors understand how the Cypress automation and supporting assets are organized.

## High-level Architecture

The repository is a Cypress automation demo built around a lightweight mock control server and test artifacts. The main components are:

- `cypress/` — Cypress test code, fixtures, support utilities, and server assets.
- `scripts/` — Node and Python helpers that run Cypress, generate reports, or inspect pages.
- `cypress.config.js` — Cypress configuration settings for test execution.
- `package.json` — dependency and script definitions.

The automation flow is:

1. Start the local `mcp-server` if the tests require mocked endpoints.
2. Run Cypress tests from `cypress/e2e/`.
3. Use fixtures and prompts to drive test data and test case generation.
4. Write outputs to `cypress/results/` and capture screenshots in `cypress/screenshots/`.
5. Review manual-testing artifacts for exploratory or documentation work.

## `cypress/mcp-server`

This folder contains the local mock control server used by Cypress tests.

- `cypress/mcp-server/cypress-server.js`
  - A small Node.js server that exposes mock endpoints and support behavior.
  - It allows tests to exercise login flows and simulated app responses without depending on a real backend.
  - Start it using:

```bash
node cypress/mcp-server/cypress-server.js
```

- Why it exists
  - Provides stable, repeatable test behavior.
  - Allows the suite to run offline or in continuous integration without external dependencies.
  - Supports test scenarios for login and application state.

## `cypress/prompts`

The `prompts` folder stores structured guidance and test generation content for the project.

- `cypress/prompts/*.prompt.md`
  - These files describe test planning, test-case generation, and execution prompts.
  - They are useful when using AI-assisted workflows or when creating manual documentation for how tests should behave.

- Common prompt types:
  - `test-plan.prompt.md` — describes the purpose and structure of the planned test suite.
  - `test-case.prompt.md` — defines individual test cases and expected behavior.
  - `cypress-execution.prompt.md` — explains how Cypress should execute the tests.

- Why it exists
  - Helps maintain a consistent testing strategy.
  - Captures the intent behind tests so manual reviewers and automation authors understand the design.

## `cypress/fixtures/manual-testing`

This folder holds manual-testing artifacts and supporting documents.

- Example contents:
  - `test-plan.md` — a manual test plan describing key workflows and coverage.
  - `test-cases.md` — manual test cases describing what should be validated.
  - `test-cases-treez-login.md` — focused manual tests for the Treez login flow.
  - `cypress-results.html` — a report generated from test results for manual review.

- Purpose:
  - Records human-readable testing notes, exploratory test ideas, and acceptance criteria.
  - Supports hybrid test workflows where automation and manual review both contribute to quality.

## `cypress/results`

This folder stores the structured output from Cypress execution.

- `cypress/results/cypress-results.json`
  - A JSON report generated by Cypress when running tests in JSON mode.
  - It can be used by scripts to produce HTML reports or CI summaries.

- How to use it
  - Run tests and collect results with `npx cypress run --reporter json --reporter-options output=cypress/results/cypress-results.json` or a project script.
  - Use `scripts/generate-cypress-results.js` to transform the JSON results into a more readable report.

## `cypress/screenshots`

This folder contains screenshots captured by Cypress when tests fail or when explicit screenshot commands run.

- Purpose:
  - Provide visual evidence of failures or key application screens.
  - Help developers diagnose what went wrong in the browser.

## How these folders work together

- `cypress/mcp-server` provides the mock backend or API behavior required by the tests.
- `cypress/e2e/` contains the actual spec files that exercise features and flows.
- `cypress/fixtures` and `cypress/prompts` provide test data and guidance for building and understanding the tests.
- `cypress/results` and `cypress/screenshots` capture execution artifacts for later review.
- `cypress/fixtures/manual-testing` holds manual test plans and documentation that support exploratory and acceptance testing.

## Recommended workflow

1. Install dependencies:

```bash
npm install
```

2. Start the mock server if needed:

```bash
node cypress/mcp-server/cypress-server.js
```

3. Run the Cypress suite:

```bash
npx cypress run
```

4. Inspect results and screenshots:

- `cypress/results/cypress-results.json`
- `cypress/screenshots/`
- `cypress/fixtures/manual-testing/`

5. Update prompts and manual-testing artifacts when new scenarios are added.

## Notes for contributors

- Use the prompts folder to document new test flows or to clarify why a test exists.
- Keep manual-testing documents aligned with automated coverage.
- Keep the mock server behavior simple and deterministic so tests remain stable.
